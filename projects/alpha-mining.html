WorldQuant Alpha 智能研究系统

我的职责

我设计研究、生成、验证、模拟和提交的状态，确定字段和算子校验、证据记录以及资料缺失时的停止逻辑。

研究资料分散，模型生成的 Alpha 公式也可能引用失效字段或不合规算子。候选必须经过筛选，才值得送去模拟。

做到哪一步

MVP · 本地校验至待模拟

独立完成研究 MVP。一次本地运行生成 10 个候选，1 个进入待模拟队列；另建立了包含 69 项检查的验证套件。

关键决策

本地生成和平台模拟分开

本地只做研究、生成和校验。通过的候选记录到待模拟队列，模拟与提交单独执行并记录平台回执。

先校验字段和算子，再让候选入队

逐项核对可信字段目录、算子、参数和表达式。缺少可信目录时暂停校验，避免把无依据的公式送入队列。

每个候选保留生成、淘汰和入队记录

分别记录生成数量、通过本地校验的数量及平台回执。回看同一轮研究时，能找到候选来源和淘汰理由。

方案与验证

从研究资料到候选

我把知识检索、研究假设、候选生成、去重、校验与历史反馈做成独立 MVP。LLM 提议表达式与解释，Prompt 和 JSON Schema 固定输出结构，记录候选来源、时间和研究上下文。

简历记录研究资料库包含 1,000+ 因子字段与 122 个算子。原作品集的本地校验版本以 5,697 个字段定义、15 个内置算子及完整算子表检查字段、算子及参数数量，两组数字对应各自的数据口径。

研究与提交的边界

历史审计中，135 次模拟有 27 次完成，记录过 89 次 HTTP 400。我把生成脚本、待模拟 CSV 队列与提交脚本分开，字段缺失、算子或参数不合法时在本地拦截，缺少认证目录则停止入队。

候选合格后只标为待模拟。研究入口本身不认证、不执行远端模拟、不生成平台 Alpha ID；授权后的模拟、提交与回执另行记录。

本地验证与外部研究记录

同一次本地运行生成 10 个候选，有 1 个满足入队条件。69 项验证覆盖字段、算子、状态和失败路径，原记录的全量运行耗时 47.8 秒。

简历另记通过 WorldQuant Brain Gold 顾问考试，并凭实际 Alpha 研究累计获得 800+ 美元顾问绩效收入。这一经历与上面的本地候选测试各有独立口径。

项目背景与范围

项目概述

  • 面向 WorldQuant Brain 的证据驱动 Alpha 研究与生成工作流，把生成、验证和提交拆成可审计状态。

业务场景

  • 证据驱动的 Alpha 研究、验证与待模拟队列。累计获得 800 美元顾问绩效收入

背景

  • 旧链路将生成、simulate、反馈和人工修复拆在多个脚本与 CSV 中，候选数量无法直接代表研究质量。历史审计基线记录过 89 次 HTTP 400，135 次 simulate 中仅 27 次 COMPLETE。需要建立边界清晰、失败关闭、证据可追溯的候选生成与入队闭环，确保研究产出与平台 simulate 结果保持分离。

目标用户

  • 量化研究者、策略开发者、Alpha 审计团队

项目目标

  • 建立证据驱动的 Alpha 研究工作流：把本地 catalog、LLM 研究、硬门禁和待 simulate 队列串成可审计链路，不伪造平台通过率。

用户痛点

  • 生成入口曾混入 factory/offline 与 READY 语义，状态容易被误读为可提交。
  • 完整字段与算子约束不足会把格式错误推迟到远端，候选阶段暴露完整 5697 字段并存在算子别名与 arity 风险。
  • 缺少 provenance 时，无法判断候选是模型生成、人工修复还是平台反馈。真实运行得到 llm_candidates=10 但只有 1 个满足入队条件。

使用场景

  • 研究者读取本地 catalog 与研究上下文，结合历史成功案例生成 Alpha 候选表达式。
  • AI 生成候选后立即执行本地硬门禁：字段完整性、算子合法性、arity 约束与状态验证。
  • 通过验证的候选写入待模拟队列（PENDING_SIMULATION），保留完整 provenance 标记来源。
  • 认证 catalog 缺失时系统保持 CATALOG_UNAVAILABLE，不允许候选进入后续流程。
  • 队列中的候选等待人工授权后再进入 simulate 与 submit，研究产出与平台结果严格分离。
产品方案与系统设计

产品方案

  • 冻结为”生成Alpha.py → 待提交Alpha列表.csv → 提交Alpha.py”三段式架构，把研究、验证、simulate、submit 分成不同状态。生成入口不认证、不 simulate、不 submit、不创建 alpha_id；缺少认证 catalog 时保持 CATALOG_UNAVAILABLE；只允许通过硬门禁的候选进入 PENDING_SIMULATION 队列。

为什么用 AI

  • LLM 适合提出研究候选表达式与解释，但候选必须经过本地字段、算子与状态门禁才能进入队列，不能让生成能力越权进入真实提交。生成、验证、simulate、submit 必须拆成不同状态。

AI 的作用

  • 把本地 catalog、LLM 研究、硬门禁和待 simulate 状态串成可审计链路

功能模块

  • 研究生成层：LLM 候选生成与 provenance 标记，记录生成来源、时间戳与研究上下文
  • 本地验证层：字段完整性校验（5697 字段）、算子合法性检查（15 个内置 + 完整 operators）、arity 约束与状态门禁
  • 队列与状态层：待模拟队列管理、状态机流转（PENDING_SIMULATION → simulate → submit）与失败恢复
  • 平台执行层：授权后的 simulate 与 submit 调用、回执处理与结果追踪
  • 审计与观察：完整操作日志、状态变更记录与边界验证测试套件（69 项验证）

系统架构

  • 研究生成层
  • 本地验证层
  • 队列与状态层
  • 平台执行层

AI 与产品分工

  • AI 负责：提出候选表达式、研究解释、字段推荐与算子组合建议
  • 规则负责：字段完整性、算子合法性、arity 约束、状态机流转与队列管理
  • 人工负责：审计边界、复核异常、授权 simulate/submit 与策略调整
  • 兜底机制：抓取失败补偿、catalog 缺失 fail-closed、验证不通过拒绝入队、异常进入可恢复队列

技术方案

  • Python 脚本与 CSV 队列：轻量级本地研究工作流，独立于平台认证与网络状态
  • 本地 catalog / operators 约束：5697 字段定义与算子库作为硬门禁依据
  • 状态机与 provenance：PENDING_SIMULATION / simulate / submit 状态流转与来源追踪
  • 测试驱动验证：69 项验证套件覆盖边界、状态、字段、算子与失败场景
  • 运行报告与审计：测试结果、队列变化、候选详情作为交付证据
需求、交付与验证

需求与验收规则

  • 生成入口不认证、不 simulate、不 submit、不创建 alpha_id
  • 缺少认证 catalog 时保持 CATALOG_UNAVAILABLE
  • 只允许通过硬门禁的候选进入 PENDING_SIMULATION

业务价值

  • 边界冻结：生成入口不认证、不 simulate、不 submit、不创建 alpha_id，避免越权操作
  • 格式前移：本地字段/算子硬门禁，不满足约束的候选在远端请求前被拒绝
  • 状态分离：llm_candidates=10 但仅 1 个入队，研究产出与平台 simulate 结果保持分离
  • 证据可追溯：相关验证套件 69 项通过，全量测试 47.8 秒内完成，队列变化可审计
  • 失败关闭机制：认证 catalog 缺失时保持 CATALOG_UNAVAILABLE，不伪造平台通过率

原案例成果描述

  • 本地运行将 10 个候选收敛为 1 个可入队样本；不伪造平台通过率

个人职责与复盘

职责概述

  • 独立完成产品边界、根因审计、架构规划与验证收口

个人工作

  • 定义生成、验证、模拟、提交的边界与状态语义，确保每个环节职责清晰
  • 审查状态语义、证据 provenance 与 fail-closed 行为，建立可追溯的审计链路
  • 设计 69 项验证套件覆盖边界场景，确保本地验证结果可在任何环境复现
  • 让 AI coding agent 执行实现，自己负责边界审计、复现验证和证据收口
  • 区分"候选生成"与"平台质量"，把工程链路通过与策略盈利/生产晋升严格分开

复盘

  • 候选数不是平台质量：必须区分研究产出（本地生成与验证）与平台结果（simulate 回执）
  • 认证、模拟和提交是高风险动作：默认应保持关闭，只在明确授权与完整上下文下执行
  • 失败关闭与 provenance 是机制：不是写在文档里的承诺，而是通过状态机与测试强制执行
  • 本地质量不等于平台成功：即使 69 项验证通过，策略盈利与生产晋升仍需真实 simulate 证据
